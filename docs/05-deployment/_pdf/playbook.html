Part 1

The plan at a glance

One small rented server in France runs the whole platform. The owner deploys it with one command from the Mac, always from tested code, always after a backup. Backups exist three times. A free alert emails both of us when the site is down. Automatic deploys from GitHub come later, and only if the client keeps the platform after the test month.

Secrets and children's data A secret is typed by a person into a terminal: never in a chat (with a person or an AI), an email, a commit or a screenshot. Production secrets are made on the server. Private SSH keys never leave the machine that made them: only the .pub line is sent. Pupils' data never leaves the server except as the owner's backup copy, and is never used for tests on a laptop.

Working together

  • One channel for production (a WhatsApp or Signal group): say before acting on the server, and after.
  • One person at a time changes something on the server.
  • First deploy in pairs: a call with screen share; the owner types, the teammate reads the logs and looks away during passwords.
  • Written trace: each production action is one line in docs/05-deployment/LOG.md; the phase status is in 03-PLAN.md.
  • With an AI agent: start it with docs/05-deployment/AGENT_PROMPT.md. The agent explains, the person runs.

Part 4

Deploy day

Replace IP with the VPS address and ngclass.com with the real domain.

1 One SSH key each

OWNER on the Mac (Terminal). The .pub line goes in the OVHcloud order.

ssh-keygen -t ed25519 -f ~/.ssh/ngclass_ovh -C "owner-ngclass"
cat ~/.ssh/ngclass_ovh.pub

TEAMMATE on Windows (PowerShell). Send the .pub line to the owner; it is public.

ssh-keygen -t ed25519 -f $HOME\.ssh\ngclass_ovh -C "teammate-ngclass"
Get-Content $HOME\.ssh\ngclass_ovh.pub

OWNER adds it on the server, then the teammate tries ssh -i $HOME\.ssh\ngclass_ovh ubuntu@IP.

ssh -i ~/.ssh/ngclass_ovh ubuntu@IP
echo 'ssh-ed25519 AAAA…the teammate line… teammate-ngclass' >> ~/.ssh/authorized_keys

2 Point the domain to the server

OWNER OVHcloud panel › domain › DNS zone: one A line for the domain and one for www, both to the VPS IP. Delete the parking A and AAAA lines. TEAMMATE checks until the answers are right:

dig +short ngclass.com          # the VPS IP
dig +short www.ngclass.com      # the VPS IP
dig +short AAAA ngclass.com     # nothing

On Windows without dig: Resolve-DnsName ngclass.com in PowerShell.

3 Deploy

OWNER on the Mac, from the project folder, with the teammate on the call:

git switch main && git pull && git status
./infra/deploy.sh ubuntu@IP

The first time, the server is prepared (time zone, updates, Docker, firewall, fail2ban, swap, nightly backup), then make-env.sh asks the domain and the owner's account: the owner types the password, the teammate looks away. The first build takes about 5 minutes. It ends with Done: https://ngclass.com is up.

4 Smoke test

curl -sI https://ngclass.com | head -1        # HTTP/2 200
curl -s https://ngclass.com/health            # {"status":"UP"}
curl -sI http://ngclass.com | head -3         # redirect to https
curl -sI https://www.ngclass.com | head -3    # redirect to the main address
  1. The owner signs in, sets a new password, sees the owner dashboard.
  2. The owner adds a test teacher; in a private window she signs in, changes the password, creates a subject and a group, uploads a PDF, plans a session.
  3. She adds a pupil with a parent; the parent signs in, changes the password, accepts the privacy notice, sees the child.
  4. On a phone: the site opens; Arabic reads right to left.
  5. Deploy again (same commit): everything is still there.

5 Harden and protect

  • Password login off (keep one session open while doing it): sudo sshd -T | grep -i '^passwordauthentication'; if yes, write PasswordAuthentication no in /etc/ssh/sshd_config.d/99-ngclass.conf, sudo systemctl reload ssh, and open a new session to check.
  • UptimeRobot (owner): an HTTP(s) monitor on https://ngclass.com/health, every 5 minutes, both emails as alert contacts.
  • OVHcloud backup (owner): visible in the VPS panel.
  • Backup now and copy it: sudo /opt/ngclass/infra/backup.sh on the server, then the copy to the Mac (Part 5).
  • Restore drill (teammate, before any real data): back up, rename the test group and upload one more file, restore, check the change is gone and the files open.
Part 5

Living with it

On the server, every command below uses this shortcut (type it once per session):

C="sudo docker compose -f /opt/ngclass/infra/docker-compose.prod.yml"

Put a new version online OWNER

  1. The change is merged into main through a pull request, CI green.
  2. Evening or weekend; say it in the channel.
  3. On the Mac:
git switch main && git pull && git status
ssh -i ~/.ssh/ngclass_ovh ubuntu@IP sudo /opt/ngclass/infra/backup.sh
./infra/deploy.sh ubuntu@IP
git rev-parse --short HEAD

The second line is the backup (part of deploy.sh once T3 is done); the last one prints the commit for LOG.md. Then smoke test steps 1 and 2, and one line in LOG.md. Browsers take the new version on their next visit.

The weekly check TEAMMATE · 10 minutes

$C ps                                      # three parts Up, api and db (healthy)
df -h /                                    # below 70 %
free -h                                    # swap used stays small
tail -7 /var/log/ngclass-backup.log        # one line per night
$C logs --since 168h api | grep -c ERROR   # look closer if it jumps
cat /var/run/reboot-required 2>/dev/null   # a reboot waits: do it in the evening

Reboot when asked, in the evening, after telling the channel: sudo reboot, then $C ps a minute later. One line in LOG.md.

Restore OWNER DECIDES

Everything written after the backup is lost. On the server, DATE is the backup's stamp, for example 2026-11-20_0200:

cd /opt/ngclass/infra
sudo docker compose -f docker-compose.prod.yml stop api
sudo docker compose -f docker-compose.prod.yml exec -T db pg_restore --clean --if-exists -U ngclass -d ngclass < /var/backups/ngclass/db_DATE.dump
sudo docker compose -f docker-compose.prod.yml run --rm --no-deps --user root -v /var/backups/ngclass:/backup --entrypoint sh api -c "rm -rf /data/files/* && tar -xzf /backup/files_DATE.tar.gz -C /data"
sudo docker compose -f docker-compose.prod.yml start api

Roll back

Code only (the usual case)

git switch --detach <good commit>
./infra/deploy.sh ubuntu@IP
git switch main

The last good commit is in LOG.md.

Code and data (last resort)

The new version changed the tables and the old code cannot run on them: restore the backup taken just before the deploy, then deploy the old commit. Anything written in between is lost.

Never down -v or delete a Docker volume (the teacher's data and the HTTPS certificate) · change DB_PASSWORD in infra/.env (PostgreSQL keeps the first one) · deploy during school hours · run two changes on the server at the same time.

When something goes wrong

First say in the channel what you see and that you are looking. Restarting and reading logs: either of us. Restore, rollback with data, telling the teacher: the owner decides.

A secret leaked

WhatDo
The owner's app passwordChange it in the app
A private SSH keyDelete its line from ~/.ssh/authorized_keys on the server; make a new key
JWT_SECRETNew value (openssl rand -hex 48) in infra/.env, then $C up -d; people stay signed in
DB_PASSWORDChange it inside PostgreSQL first, then in .env, then $C up -d
Anything pushed to GitHubThe repository is public: change the secret, deleting the commit is not enough

Note it in LOG.md, without the value.

Telling the teacher

Short, in her language, no technical words; only when she is affected.

Down« La plateforme est momentanément indisponible. Nous corrigeons, retour prévu vers HH:MM. Vos données sont en sécurité. »
Back« La plateforme fonctionne à nouveau. Merci de votre patience. »

After a serious incident, five lines in LOG.md within two days: what, when, why, what fixed it, what prevents it next time.
